    入门

    Fynvra 是什么，界面怎么分工What Fynvra is, and how the window is laid out

    Fynvra 是一个本地运行的多 Agent 编程工作台。你只和主 Agent 对话；它把需求拆成任务，交给各自的 Worker，再审查和合并。这一页先对应真实界面，告诉你每一块在哪里、下一步点哪里。 Fynvra is a local multi-agent coding workbench. You talk to one orchestrator; it splits the request into tasks, hands each to its own worker, then reviews and merges. This page maps the real window so you know where everything is and what to click next.

    界面一眼看懂The window at a glance

    窗口顶部是标题栏：左边开关左栏，右边是设置、主题和右侧面板。设置会覆盖整个窗口，按 Esc 或右上角的关闭按钮返回。标题栏下面分成三块。

    左栏

    工作区 → 会话

    “工作区”标题右侧的 + 挂入目录。每个工作区用左侧箭头展开会话；会话行显示状态点、角色徽标和更新时间。

    中间

    对话与文件标签

    顶部标签条固定有「对话」。打开文件、终端或 diff 后出现新标签。对话里从上到下是标题、消息、审批条、输入框和底部状态栏。

    右栏

    文件 / 任务 / 改动

    「任务」标签上显示当前编排的任务数。右栏左边缘可拖动调宽，双击恢复默认宽度。

    第一次打开还没有工作区时，中栏只有「挂入目录」按钮，右栏会提示先选择工作区。挂入一个目录后，再新建会话。

    The title bar sits on top: the left sidebar toggle on one side, Settings, theme, and the right panel on the other. Settings covers the window; press Esc or use the close button to return. Below it the window splits into three areas.

    Left

    Workspaces → sessions

    Use + next to “Workspaces” to attach a folder. The chevron expands sessions for each workspace; a session row shows a status dot, role badge, and relative time.

    Center

    Chat and file tabs

    The tab strip always includes “Chat”. Opened files, terminals, and diffs add tabs. A chat runs from title, messages, and approval bar down to the composer and status bar.

    Right

    Files / Tasks / Changes

    The Tasks tab shows the number of tasks in the current run. Drag the panel’s left edge to resize it, or double-click to restore the default width.

    On first launch there is no workspace yet: the center shows only “Attach folder”, and the right panel asks you to pick a workspace. Attach a folder first, then create a session.

    五个词Five terms

    工作区
    挂进来的一个目录。有 git 时按仓库编排，每个任务用独立 worktree；没有 git 的目录显示「无 git」，按原地模式工作。
    会话
    一次和某个角色的对话。状态有空闲、运行中、等待审批、出错。会话记录保存在本机。
    主 Agent
    内置的 Orchestrator 角色。拆任务、派活、审查、合并，默认自己不改代码。新建会话时默认选它。
    Worker
    接到一个任务的 Agent。它在自己的 git worktree 里改代码，做完向主 Agent 汇报；无 git 时直接在挂入的目录里改。
    收件箱
    Worker 和主 Agent 之间的消息：提问、答复、指示、完成汇报。任务详情里能看到整条消息流；主 Agent 空闲时会被新消息唤醒。
    Workspace
    A folder you attach. A Git repository is orchestrated with a separate worktree per task; a plain folder shows “No git” and runs in place.
    Session
    A conversation with one role. Status is idle, running, waiting for approval, or error. Session records stay on this computer.
    Orchestrator
    The built-in main agent. It plans, dispatches, reviews, and merges, and by default does not edit code. New sessions select it by default.
    Worker
    An agent given one task. It edits in its own Git worktree and reports back; without Git it edits the attached folder in place.
    Inbox
    Messages between a worker and the orchestrator: questions, replies, instructions, and done reports. The task details show the stream; an idle orchestrator wakes when a new message arrives.

    1. Launch the app

    入门

    第一次运行：从模型到第一次派发First run: from a model to the first dispatch

    按下面五步操作，第一次使用就能完成“连接模型 → 挂入目录 → 新建会话 → 发出需求 → 查看改动”。每一步都对应界面上的实际按钮。 Five steps take you from “connect a model” to “attach a folder, create a session, send a request, and inspect the changes”. Each step names the actual control in the window.

    1. 连接模型服务1. Connect a provider

    按 Ctrl+,（macOS 为 ⌘+,）打开设置，进入「模型服务」。点「添加服务」，选择预设，或用自定义 OpenAI 兼容地址；填写 Base URL 和 API Key，拉取或手动添加模型 id，打开需要思考档位的模型的「推理」，保存。

    回到主窗口，在输入框左下角能看到模型胶囊，说明服务已可用。详细字段见 模型服务。

    Press Ctrl+, (⌘+, on macOS), open Settings, and choose Model providers. Click Add provider, pick a preset or a custom OpenAI-compatible endpoint, fill in the base URL and API key, fetch or type model ids, turn on Reasoning for models that should offer thinking levels, and save.

    Back in the main window, the model pill at the bottom-left of the composer confirms the provider is available. See Providers for every field.

    2. 挂入一个工作区2. Attach a workspace

    在左栏「工作区」标题右侧点 +，或在空状态点「挂入目录」，然后选一个 Git 仓库（普通文件夹也可以）。工作区项会显示名称和路径；再次点击当前工作区会展开它的会话列表。要用独立 Git worktree 派发，仓库需要已有提交。

    普通文件夹也能创建会话并派发 Worker，但会显示「无 git」，Worker 直接在目录里改，不建 worktree；同一目录一次只派一个任务。需要并行派发时请使用 Git 仓库。

    Click + next to “Workspaces” in the left sidebar, or choose “Attach folder” in the empty state, then pick a Git repository (a plain folder works too). The workspace row shows its name and path; click the selected workspace again to expand its session list. To dispatch into separate Git worktrees, the repository must already have commits.

    Plain folders can also run sessions and dispatch workers, but they show “No git”; the worker edits the folder in place, no worktree is created, and only one task runs there at a time. Use a Git repository when you need parallel dispatch.

    3. 新建会话并选角色3. Create a session and pick a role

    展开工作区后，在「会话」标题右侧点 +；也可以在中间点「新建会话」。弹层默认选中 Orchestrator（带皇冠标记），要单干可以直接选 Worker 或自定义角色。选好模型和可用的思考档位，点「创建」。

    会话打开后，标题栏显示状态、角色和当前分支；底部输入框可以开始写需求。

    Expand the workspace and click + next to the “Sessions” heading, or use “New session” in the center. The dialog selects Orchestrator (marked with a crown) by default; choose Worker or a custom role if you want to work directly. Pick a model and an available thinking level, then click Create.

    The open session shows its status, role, and current branch in the header. The composer at the bottom is ready for your request.

    4. 发出第一条需求4. Send the first request

    用平时的语言写清楚目标，按 Enter 发送，Shift+Enter 换行。运行中按钮会变成「排队」，同时出现「停止」；消息和工具调用会依次出现在时间线上。

    第一次派发时，主 Agent 会读代码、拆任务。右栏「任务」标签上出现任务数量，点进去可以看到任务卡片和进度。

    Describe the goal in your own words and press Enter to send; use Shift+Enter for a new line. While the turn runs, the send button becomes Queue and a Stop button appears; messages and tool calls stream into the timeline.

    On the first dispatch the orchestrator reads code and splits the work. The Tasks tab on the right gains a task count; open it to see task cards and progress.

    5. 查看它做了什么5. Inspect what happened

    在右栏「任务」里点一张任务卡片，任务详情会显示任务书、依赖、尝试、消息和 Worker 输出。任务处于「待验收」或「已完成」且有 git 时，点「查看改动」会切到「改动」标签并打开这次任务的 diff。

    主 Agent 会在对话里汇报审查和合并结果。如果需求不清楚，Worker 的提问会由主 Agent 带回对话；直接在输入框回答即可。

    In the right panel’s Tasks tab, click a task card. Details show the brief, dependencies, attempts, messages, and worker output. When the task is In review or Completed and uses Git, click View changes to switch to the Changes tab with that dispatch’s diff.

    The orchestrator reports review and merge results in the conversation. If the request is unclear, worker questions come back through the orchestrator; answer them in the composer.

    worktree 派发条件Worktree dispatch requirements

    要用独立 Git worktree 派发，需要一个已有提交的 Git 仓库，并且本机配置了 Git 用户名和邮箱。普通文件夹仍可创建会话和派发 Worker，但 Worker 原地修改，同一目录一次只派一个任务。Windows 上建议安装 Git for Windows；如果找不到 Bash，到「设置 → 通用」里指定 Windows 本地命令壳。

    To dispatch into separate Git worktrees, you need a Git repository that already has commits plus a local Git user name and email. Plain folders can still run sessions and dispatch workers, but a worker edits in place and only one task runs in that folder at a time. On Windows, Git for Windows is recommended; if Bash cannot be found, set the local agent shell under Settings → General.

    工作区与会话

    添加工作区，管理目录与会话Add workspaces and manage folders

    工作区就是你挂进 Fynvra 的目录，也是所有会话和任务的根。左栏的每个工作区都可以展开成一棵会话列表；同一时间只查看一个工作区。 A workspace is a folder attached to Fynvra and the root for every session and task. Each workspace in the sidebar expands into its own session list; only one workspace is viewed at a time.

    挂入一个目录Attach a folder

    1. 找到添加入口

      左栏「工作区」标题右侧的 +；工作区为空时，中栏也有「挂入目录」按钮。

    2. 在系统目录选择器里选文件夹

      选 Git 仓库的根目录。若选了仓库里的子目录，Fynvra 会询问是挂入仓库根目录，还是把子目录按普通目录挂入；按普通目录挂入时不会建 worktree。

    3. 确认左栏出现工作区

      工作区行显示名称和路径。Git 仓库显示文件夹图标；普通目录带「无 git」徽标。

    4. 展开会话

      点工作区左侧的箭头，或再次点击已选中的工作区，展开它下面的「会话」分组。

    1. Find the add control

      Use + next to “Workspaces” in the left sidebar, or the “Attach folder” button in the empty center area.

    2. Pick a folder in the system dialog

      Choose the Git repository root. If you pick a subfolder inside a repository, Fynvra asks whether to attach the repository root or the subfolder as a plain folder; the plain-folder option creates no worktrees.

    3. Confirm the workspace row

      The row shows the folder name and path. Git repositories get a folder icon; plain folders carry a “No git” badge.

    4. Expand its sessions

      Click the chevron at the left of the workspace, or click the selected workspace again, to open the Sessions group underneath.

    展开、切换与搜索会话Expand, switch, and search sessions

    每个工作区可以独立展开。展开「会话」分组后，标题右侧有搜索按钮和新会话 +。点会话行会切换到该会话；展开其他工作区只加载它的列表，不会改变当前正在查看的会话。

    搜索会话时，点搜索图标或按 Ctrl+K（macOS 为 ⌘+K），在会话列表上方输入标题关键字。按 Enter 打开第一个结果，Esc 清空并收起搜索。

    Each workspace expands independently. Inside the Sessions group, the heading has a search button and a new-session +. Clicking a session switches to it; expanding another workspace loads its list without changing the session you are viewing.

    To search sessions, click the search icon or press Ctrl+K (⌘+K on macOS), then type a title fragment above the list. Enter opens the first result; Esc clears and closes the search.

    工作区的更多操作More workspace actions

    把鼠标移到工作区行上，点右侧的省略号；也可以在行上右键。菜单里有：

    • 打开于：用 VS Code、文件管理器或自定义应用打开该目录。自定义应用需要先选择程序并命名。
    • 复制路径 / 复制名称 / 复制当前分支：只复制文本；分支项只在 Git 工作区出现。
    • 从列表移除：把工作区从 Fynvra 列表里移除，不会删除磁盘上的项目目录。

    Hover a workspace row and click its ellipsis, or right-click the row. The menu offers:

    • Open in: open the folder in VS Code, the file manager, or a custom app. A custom app must be selected and named first.
    • Copy path / Copy name / Copy current branch: copy text only; the branch item appears for Git workspaces.
    • Remove from list: removes the workspace from Fynvra; it does not delete the project folder on disk.

    Git 工作区的 worktreeWorktrees in a Git workspace

    主 Agent 每次派发会给任务建一个独立的 git worktree，分支名是 fynvra/<slug>。默认放在仓库同级的 <仓库目录名>-worktrees，可以在「设置 → 通用 → Worktree 位置」里选择其他目录或恢复默认；「磁盘占用」会列出每个工作区当前的 worktree 数量和大小。

    任务合并后主 Agent 会清理对应 worktree。需要临时看某个已清理 worktree 的历史改动时，从任务详情的「查看改动」进入。

    For each dispatch the orchestrator creates a separate Git worktree on branch fynvra/<slug>. By default it sits beside the repository as <repo>-worktrees. Change the location or restore the default under Settings → General → Worktree location; Disk usage lists the worktree count and size per workspace.

    After a merge the orchestrator cleans up that worktree. To inspect saved changes from a cleaned worktree, open the task details and click View changes.

    没有 gitNo git

    普通文件夹仍可创建会话并派发 Worker，只是走原地模式：不建 worktree，Worker 直接改这个目录，审查时列出它汇报的文件。并行的 Worker 会共用同一份文件，所以一次只派一个任务。

    A plain folder can still run sessions and dispatch workers, but it runs in place: no worktree, workers edit that folder, and review lists the files they reported. Parallel workers would share those files, so dispatch one task at a time.

    工作区与会话

    新建、切换与管理会话Create, switch, and manage sessions

    会话是一次和某个角色的对话。新建时选角色、模型和思考档位；之后在左栏切换，或在同一个工作区里搜索标题。运行中的会话会明确显示状态。 A session is one conversation with a role. Create it with a role, model, and thinking level; then switch from the left sidebar or search by title within the workspace. Running sessions show their state clearly.

    新建会话Create a session

    1. 选择入口

      展开工作区后，点「会话」标题右侧的 +；或在中间点「新建会话」。两者打开同一个弹层。

    2. 选角色

      列表来自「设置 → 角色」，默认选 Orchestrator。只想让一个 Agent 直接干活时选 Worker；自定义角色也可以在这里选。

    3. 选模型和思考档位

      模型下拉按服务分组。模型支持推理时，下方会出现思考档位；不支持或服务不可用时会给出提示。

    4. 点「创建」

      会话创建后自动选中，左栏出现新行，中间进入对话视图。没有可用模型服务时，先回「设置 → 模型服务」添加。

    1. Choose an entry point

      Expand a workspace and click + next to the Sessions heading, or click “New session” in the center. Both open the same dialog.

    2. Pick a role

      The list comes from Settings → Roles and starts on Orchestrator. Choose Worker when one agent should work directly, or pick a custom role.

    3. Pick a model and thinking level

      The model select is grouped by provider. If the model supports reasoning, thinking levels appear below; otherwise the dialog explains what is missing.

    4. Click Create

      The new session is selected automatically, appears in the sidebar, and opens in the chat view. If no provider is available, add one under Settings → Model providers first.

    切换和搜索Switch and search

    在左栏展开工作区后点会话行即可切换。中间的会话标题栏会显示状态点、标题、角色徽标和当前分支；底部状态栏显示 token、费用、审批档位、分支和模型。

    快捷键：Ctrl+Shift+[ 上一个会话，Ctrl+Shift+] 下一个会话；Ctrl+K 打开会话搜索。macOS 上把 Ctrl 换成 ⌘。

    Expand a workspace and click a session row to switch. The center header shows the status dot, title, role badge, and current branch; the status bar shows tokens, cost, approval mode, branch, and model.

    Shortcuts: Ctrl+Shift+[ for the previous session, Ctrl+Shift+] for the next, and Ctrl+K for session search. Use ⌘ instead of Ctrl on macOS.

    协作与审查

    主 Agent 如何拆任务、派发与合并How the orchestrator splits, dispatches, and merges

    你只和主 Agent 对话。它读代码、拆任务、为每个任务派一个 Worker，再审查结果、合并或打回。界面上的「任务」和「改动」是这条流程的只读视图；控制通过对话完成。 You talk only to the orchestrator. It reads code, splits work, gives each task its own worker, then reviews and either merges or sends the work back. Tasks and Changes are read-only views of that flow; control happens in the conversation.

    一轮编排One orchestration loop

    1. 拆任务

      读够用的代码，把需求分成边界清楚、尽量能并行的任务，并写一份 Worker 能独立执行的任务说明。任务之间的依赖会记在派发里。

    2. 派发

      在 Git 工作区，每个任务一个 Worker，单独的 git worktree，分支名是 fynvra/<slug>。默认放在仓库同级的 <仓库目录名>-worktrees，可在「设置 → 通用」里改位置。普通文件夹不建 worktree：Worker 直接在挂入的目录里改，同一目录一次只派一个任务。没有指定角色时用默认的 Worker。

    3. 验收

      Worker 汇报后，主 Agent 看 diff、跑检查。通过就合并（merge --no-ff）并清理 worktree；不行就打回，Worker 再改，形成新的尝试。

    1. Split the work

      The orchestrator reads just enough code to split the request into tasks with clear ownership, ideally parallel, and writes a brief each worker can follow alone. Dependencies between tasks are recorded in the dispatch.

    2. Dispatch

      In a Git workspace, each task gets its own worker and Git worktree on fynvra/<slug>. By default that folder sits beside the repo as <repo>-worktrees; change the location under Settings → General. Plain folders create no worktree: the worker edits the attached folder in place, and only one task runs there at a time. Dispatch uses the default Worker role when none is named.

    3. Review

      When a worker reports done, the orchestrator reads the diff and runs checks. A pass is merged with merge --no-ff and the worktree is cleaned up; otherwise the work is sent back, creating a new attempt.

    派发方式与默认边界Dispatch modes and default boundaries

    • Git 仓库（worktree 隔离）：已有一个提交，且本机配置了 Git 用户名和邮箱。每个任务在独立 worktree 中执行；Windows 上建议安装 Git for Windows，找不到 Bash 时在「设置 → 通用」指定 Windows 本地命令壳。
    • 普通目录（原地模式）：不需要 Git，Worker 直接修改挂入的目录；同一目录一次只派一个任务，也没有 worktree diff。
    • 默认 Worker：派发时没有指定角色就用 Worker；Worker 默认「全部工具 + 自动接受编辑」。
    • 主 Agent 不改代码：Orchestrator 的工具策略是「编排」，只能读、只读 Git 和派发/审查/合并工具，即使审批是「完全放行」也不能写文件或执行任意命令。
    • 任务状态：待开始 → 进行中 → 待验收 → 已完成；走不下去会标成失败或已放弃。改动以未提交 / 已提交分组，在任务详情里查看。
    • Git repository (worktree isolation): it already has a commit, and a local Git user name and email are configured. Each task runs in its own worktree. On Windows, Git for Windows is recommended; if Bash is missing, set the local agent shell under Settings → General.
    • Plain folder (in place): Git is not required; the worker edits the attached folder directly. Only one task runs there at a time, and there is no worktree diff.
    • Default Worker: dispatch uses Worker when no role is named; Worker defaults to All tools + Auto-accept edits.
    • The orchestrator does not edit code: its tool policy is Orchestration — read files, read-only Git, and dispatch/review/merge tools. Even with Full approval it cannot write files or run arbitrary commands.
    • Task status: Not started → In progress → In review → Completed; work that cannot continue becomes failed or abandoned. Changes are grouped into uncommitted and committed in the task details.

    你如何控制流程How you steer the flow

    在主 Agent 的输入框里补充需求、回答问题、要求重试、打回或合并。任务抽屉不提供合并 / 打回按钮：它展示任务书、依赖、尝试、消息、Worker 输出和改动，具体决定由主 Agent 执行。

    Use the orchestrator’s composer to add requirements, answer questions, request a retry, reject, or merge. The task drawer has no merge or reject buttons: it shows the brief, dependencies, attempts, messages, worker output, and diff; the orchestrator executes the decision.

    Tool calls that need your confirmation appear in the approval bar or the top banner. The approval mode decides whether ordinary operations ask step by step. Protected operations still need separate confirmation in every mode; see Approvals.

    完全放行常规工具自动通过。Orchestrator 默认是这个，但它的工具策略仍然不能改代码。

    档位只决定是否弹出审批，不扩大工具能力。工具策略仍然决定这个角色能不能写文件、执行命令或只读。

    ModeBehavior
    SupervisedCommands, edits, writes, and MCP calls all wait for Allow.
    Auto-accept editsFile edits and writes pass automatically; commands and MCP still ask. This is the Worker default.
    FullOrdinary tools pass automatically. This is the Orchestrator default, but its tool policy still cannot edit code.

    The mode only decides whether an approval prompt appears; it does not broaden capability. The tool policy still decides whether a role may write files, run commands, or only read.

    处理一次审批Respond to an approval

    有请求时，会话状态变成「等待审批」，输入框上方出现审批条。审批条显示类型（执行命令 / 编辑文件 / 写入文件 / MCP 工具）、标题和可展开的详情；一次显示一条，更多请求会标出剩余数量。

    按钮有三个：「拒绝」不让这次调用继续；「本会话都允许」允许当前会话里同类的后续请求；「允许」只放行这一次。提交期间按钮禁用。其他工作区也在等待时，窗口顶部会出现「有 N 项操作等待你确认」，点「查看并处理」按会话集中处理，不会改变你当前正在看的会话。

    When a request is waiting, the session status becomes Waiting for approval and the approval bar appears above the composer. It shows the kind (command / file edit / file write / MCP tool), title, and expandable details; one request is shown at a time with a count for the rest.

    Deny stops this call; Allow for session permits subsequent requests of the same kind in this session; Allow permits just this one. Buttons disable while submitting. If other workspaces are waiting too, a banner near the top says “N operations are waiting for your confirmation”. Review and resolve handles them grouped by session without changing the session you are viewing.

    保护底线Hard floor

    始终确认Always confirmed

    git push、git reset --hard、rm -rf 这类保护操作，在任何审批档位下都要你确认。「本会话都允许」也不会豁免它们。

    Protected operations such as git push, git reset --hard, and rm -rf need your confirmation in every approval mode. Allow for session does not exempt them.

    密钥怎么存How keys are stored

    密钥Keys

    API Key 的明文只在主进程使用，界面上回显成掩码。它保存在本机配置文件里，不是加密凭证库。不要把应用数据目录、配置导出或带密钥的日志发给别人。删除一个服务后，引用它的角色需要重新选择模型。

    配置可复用的角色Configure reusable roles

    工具策略与 IDTool policies and ids

    工具策略有三档：

    • 全部工具：可以读、写、执行命令。Worker 默认用这个。
    • 只读：不能改文件，也不能执行任意命令。
    • 编排：读文件、只读 git，以及派发、审查、合并等编排工具。不能写文件或执行任意命令。Orchestrator 默认用这个，所以即使审批是「完全放行」，它自己也不会改代码。

    角色 ID 只能是小写字母、数字和连字符，不能以连字符开头或结尾，保存后不能改。派发时如果没有指定角色，用默认的 Worker。

    There are three tool policies:

    • All tools: read, write, and run commands. This is the Worker default.
    • Read-only: no file edits and no arbitrary commands.
    • Orchestration: read files, read-only git, and the dispatch, review, and merge tools. No writes and no arbitrary commands. This is why the Orchestrator still doesn't edit code when its approval mode is Full.

    A role id uses lowercase letters, digits, and hyphens, cannot start or end with a hyphen, and cannot change after save. Dispatch uses the Worker role when none is named.

    • Git 与命令代理：沿用现有环境或手动填写无认证的 HTTP/HTTPS 代理；可以测试 GitHub API 和远程仓库连通性。
    • Worktree 位置：选择自定义目录或恢复默认；「磁盘占用」列出每个工作区的 worktree 数量与大小。
    • 会话：闲置归档天数、归档时清理 worktree、归档多久后删除记录。
    • 时间线：精简只读工具、运行中展开文件改动、思考时展开、折叠历史轮次。
    • 应用更新：正式版显示当前版本、检查更新和安装状态；开发模式提示不检查更新。

    Settings → General also contains:

    • Shell: on Windows, choose the local command shell for agent commands and the terminal shell; elsewhere choose the login shell for terminals. Applies to new sessions or terminals.
    • Git and command proxy: use the existing environment or a manual unauthenticated HTTP/HTTPS proxy, with a connection test for the GitHub API and a remote repository.
    • Worktree location: pick a custom folder or restore the default; Disk usage lists worktree count and size per workspace.
    • Sessions: idle archive days, clean worktrees on archive, and days before archived records are deleted.
    • Timeline: compact read-only tools, expand edits while running, expand thinking, and fold history turns.
    • App updates: release builds show the current version, check, and install state; dev mode states that it does not check.

    通知Notifications

    「设置 → 通知」可以开关桌面通知，并分别控制是否只在主 Agent 完成时通知、Worker 提问与审批请求是否通知，以及是否播放声音。改完可以发送一条测试通知确认系统权限。

    Settings → Notifications toggles desktop notifications, whether only main-agent completion triggers them, whether worker questions and approval requests do, and sound. Send a test notification to confirm system permission.

    用量Usage

    「设置 → 用量」按今天 / 7 天 / 30 天 / 90 天统计预估费用、tokens、会话与消息数、活跃时长，并给出按角色、模型、工作区、时段和编排结果的分布。费用按记录的模型单价估算，只在这台电脑上计算。

    Settings → Usage summarizes estimated cost, tokens, sessions, messages, and active time for today / 7 / 30 / 90 days, with breakdowns by role, model, workspace, hour, and orchestration outcome. Costs are estimated from recorded model prices and computed on this computer.

    数据、安全边界与更新Data, guardrails, and updates

    Fynvra 在本机运行，设置、会话和密钥都落在本机应用数据目录。文件访问限制在已挂入的工作区；Agent 和 MCP 仍可能执行命令或访问外部服务，所以工具策略和审批档位要按项目来设。 Fynvra runs on your machine; settings, sessions, and keys live in the local app-data directory. File access is limited to attached workspaces, but agents and MCP can still run commands or reach external services, so set tool policy and approval mode per project.

    数据放在哪里Where data lives

    设置、角色、模型服务、MCP 和会话都在本机应用数据目录里，不要提交到 Git，也不要打包发给别人。开发版默认用 fynvra-dev，和安装版分开。只有开发模式才认环境变量 FYNVRA_USER_DATA_DIR。

    系统提示词、指令文件正文等大段文本不写进 settings.json；角色和指令文件各自保存在数据目录里。API Key、MCP 环境变量和 Header 的明文只在主进程读取，界面显示掩码或键名。

    Settings, roles, providers, MCP, and sessions live in the local app data directory. Don't commit that folder or send it to anyone. Dev builds use fynvra-dev, separate from an installed release. FYNVRA_USER_DATA_DIR is honored only in dev mode.

    Large text such as system prompts and instruction files is not stored in settings.json; roles and instruction entries live in their own files in the data directory. Plaintext API keys, MCP environment values, and headers are read only by the main process; the UI shows masks or key names.

    安全边界Guardrails

    • 文件读写限制在已挂入的工作区。渲染进程不能直接使用 Node.js 或 Electron。
    • Agent 和 MCP 仍然可以执行命令或访问外部服务，所以工具策略和审批档位要按项目来设。
    • 删除工作区只从列表移除，不删除磁盘目录；删除会话从列表移除，底层记录保留。归档不会自动删除仍在使用或未合并的 worktree。
    • 受保护操作（如 git push、git reset --hard、rm -rf）在任何审批档位下都要确认。
    • File access is limited to attached workspaces. The renderer cannot use Node.js or Electron directly.
    • Agents and MCP can still run commands or reach external services, so set the tool policy and approval mode per project.
    • Removing a workspace only removes it from the list; deleting a session removes it from the list while keeping the underlying record. Archiving does not delete worktrees that are still in use or unmerged.
    • Protected operations such as git push, git reset --hard, and rm -rf require confirmation in every approval mode.

    更新Updates

    已安装的 Windows 版，以及带 Developer ID 签名的 macOS 版，会在启动时和之后每 4 小时检查更新，下载完成后等你确认再重启安装。未签名的 Mac 包请从 Releases 手动下载覆盖。开发模式（pnpm dev）不检查更新。Linux 目前没有自动更新。

    「设置 → 通用 → 应用更新」显示当前版本和检查状态；有更新时按提示重启安装。

    Installed Windows builds, and macOS builds signed with a Developer ID, check at startup and every 4 hours. The download installs after you confirm a restart. Unsigned Mac builds are replaced by hand from Releases. Dev mode (pnpm dev) does not check for updates. Linux has no auto-update yet.

    Settings → General → App updates shows the current version and check state; follow the prompt to restart and install when an update is ready.

01 / INSTALL

安装与平台Install and platforms

先拿到安装包，或者从源码启动开发版；两条路径都通向同一个模型设置入口

Start from an installer or run the dev build from source. Both paths lead to the same model setup.

下载安装包Download an installer

安装包发布在 GitHub Releases 的 Assets 里；只有源码的 Source code 下载项不包含安装程序

Installers are attached to GitHub Releases under Assets. The “Source code” downloads do not include an installer.

平台Platform 安装包Installer 更新方式Updates
Windows x64 NSIS .exe 正式安装版支持应用内自动更新Installed builds support in-app auto-update
macOS Intel / Apple Silicon .dmg / .zip Developer ID 签名、公证版可自动更新；手动包需覆盖安装Developer ID-signed and notarized builds auto-update; manual builds are replaced by hand
Linux AppImage（仅构建配置）AppImage (build config only) 有构建配置，尚未纳入自动发布与更新Build config exists; not in automated releases or updates yet

macOS 首次打开First launch on macOS

把应用从 DMG 拖进「应用程序」后再启动；没有 Apple 凭证的包使用临时签名，系统可能提示无法验证开发者；确认来源可信后，到「系统设置 → 隐私与安全性」对本应用选择「仍要打开」，不需要关闭系统安全检查

Drag the app from the DMG into Applications before launching. Builds without Apple credentials are ad-hoc signed, so macOS may warn that the developer cannot be verified. After trusting the source, choose Open Anyway for this app under System Settings → Privacy & Security. You do not need to disable system security checks.

从源码运行Run from source

需要 Node.js 22.19.0 或更高（推荐 22）、pnpm 10.26.2，以及 Git

You need Node.js 22.19.0 or later (22 recommended), pnpm 10.26.2, and Git.

bashterminal
npm install --global pnpm@10.26.2
git clone https://github.com/LAIJiangFeng/fynvra.git
cd fynvra
pnpm install --frozen-lockfile
pnpm dev

首次运行需要联网下载依赖与 Electron；开发版数据目录是系统应用数据目录下的 fynvra-dev，与安装版分开；仓库不需要 .env，模型密钥在设置界面填写

The first run needs network access to download dependencies and Electron. Dev builds store data in fynvra-dev under the system app-data directory, separate from installed builds. The repository does not need a .env; model keys are entered in Settings.

首次启动First launch

  1. 打开「设置 → 模型服务」，添加服务或从本机导入Open Settings → Model providers, add a provider, or import one from this computer
  2. 挂入一个 git 仓库或普通文件夹Attach a git repository or a plain folder
  3. 新建会话，选择 Orchestrator、模型与思考档位Start a session and choose Orchestrator, a model, and a thinking level
  4. 直接描述需求，主 Agent 会决定拆不拆任务Describe the request; the orchestrator decides whether to split it

模型服务是第一步的前提；没有可用的服务与 API Key，会话无法请求模型

Provider setup comes first. A session cannot call a model without a usable provider and API key.

02 / MODELS

模型与本机导入Models and local import

服务协议、API Key、模型列表与思考档位，都在「设置 → 模型服务」里管理

Protocols, API keys, model lists, and thinking levels all live under Settings → Model providers.

添加模型服务Add a provider

选择预设或自定义 OpenAI 兼容服务，填写名称、协议、Base URL、API Key 与模型 id；使用官方地址时 Base URL 可以留空

Pick a preset or a custom OpenAI-compatible endpoint, then fill in the name, protocol, base URL, API key, and model id. Leave the base URL blank to use the official endpoint.

  • 拉取模型列表：把远端模型加入列表；也可以手动输入模型 idFetch models: add remote models to the list, or type a model id manually
  • 推理：打开后，会话与角色里才能选择思考档位Reasoning: enables thinking-level choices in sessions and roles
  • 每个服务最多保存 500 个模型，超出的模型不会加入Each provider stores up to 500 models; extra models are not added

从本机导入Import from this computer

打开「从本机导入」，勾选来源后扫描；只读取带 API Key 或自定义地址的配置；导入前可以预览、去重，并为每个服务依次选择要加入的模型

Choose Import from this computer, pick sources, and scan. Only configs with an API key or custom URL are read. Preview, deduplicate, and pick models for each provider before saving.

Claude Code~/.claude/settings.json
Codex~/.codex/config.toml
CC Switch~/.cc-switch/cc-switch.db

已有地址与 API Key 都相同的服务会被标记为重复；导入后仍需保存，删除某个服务后，引用它的角色需要重新选择模型

Providers with the same URL and API key are marked as duplicates. Imported entries still need saving, and roles that referenced a deleted provider must choose a new model.

选择模型Choose a model

新建会话时选择模型与思考档位；会话内按 Ctrl+M（macOS 为 ⌘+M）打开模型选择器；只列出已启用且填了 API Key 的服务

Pick a model and thinking level when creating a session. Inside a session, Ctrl+M (⌘+M on macOS) opens the model picker. Only enabled providers with an API key are listed.

  • 角色可以选择「跟随会话模型」；Worker 角色没配模型时，继承主 Agent 当前模型与档位A role can follow the session model; a worker role without its own model inherits the orchestrator’s current model and level
  • 会话运行中不能换模型；空闲时切换，下一次发送生效，已有对话历史保留A running session cannot switch models. Change it while idle; the next prompt uses the new model and history is preserved
  • 可选档位由模型能力决定，pi 目录之外的模型按服务里的「推理」标记判断Available levels come from model capabilities; models outside the pi catalog use the provider’s Reasoning flag

思考档位Thinking levels

思考档位决定模型回答前投入多少推理；服务未标记推理，或读不到档位时，界面会给出说明或回落到模型默认档位

The thinking level controls how much reasoning the model spends before answering. If reasoning is off or levels cannot be read, the UI explains why or falls back to the model default.

档位Level含义Meaning
off关闭思考No thinking
minimal极少思考Barely any
low少量思考Light
medium适中，日常改动通常够用Balanced; usually enough for everyday edits
high深入思考Deep
xhigh更深入的思考Deeper
max最大思考；更慢，也更耗额度Maximum; slower and uses more quota

密钥边界Key boundary

API Key 的明文只在主进程使用，界面回显为掩码；它保存在本机配置文件中，不是加密凭证库；不要分享应用数据目录、配置导出或包含密钥的日志

Plaintext API keys stay in the main process and appear masked in the UI. They are stored in local config files, not an encrypted vault. Do not share the app data directory, config exports, or logs containing keys.

03 / WORKSPACE

工作区与会话Workspaces and sessions

工作区是一个目录，会话是一次与某个角色的对话；文件、终端和任务面板都围绕当前工作区展开

A workspace is a folder; a session is a conversation with one role. Files, terminals, and the task panel all follow the current workspace.

挂入目录Attach a folder

在左侧「工作区」选择挂入目录，挑一个 git 仓库或普通文件夹；挂入 git 仓库的子目录时，会询问改挂仓库根目录、仍然按普通目录挂入该子目录，或取消

Under Workspaces in the sidebar, choose Attach folder and pick a git repository or a plain folder. If you pick a subdirectory of a git repository, Fynvra asks whether to attach the repository root, attach the subdirectory as a plain folder, or cancel.

  • git 仓库：每个任务创建独立 worktree，默认放在仓库同级的 <仓库目录名>-worktrees，可在「设置 → 通用」修改根目录Git repository: each task gets a worktree, by default beside the repo as <repo>-worktrees. Change the root under Settings → General
  • 普通文件夹：原地模式，不创建 worktree；并行的 Worker 会共用目录Plain folder: in-place mode, no worktree; parallel workers would share the folder
  • 仓库需要已有提交，并配置 git 用户名与邮箱，才能派发任务Dispatching needs an existing commit plus a configured git user name and email

新建与管理会话Create and manage sessions

点「新建会话」，选择角色（多 Agent 协作选内置 Orchestrator）、模型与思考档位；会话状态分为空闲、运行中、等待审批与出错

Choose New session, then a role (use the built-in Orchestrator for multi-agent work), model, and thinking level. Session status is idle, running, waiting for approval, or error.

  • 左侧栏按工作区列出会话；可以搜索、切换、归档或删除The sidebar lists sessions per workspace; search, switch, archive, or remove them
  • 归档只是把会话移出默认列表；归档闲置策略可在设置里调整，删除会话不删除本地 pi jsonl 记录Archiving hides a session from the default list; idle-archive rules are configurable, and removing a session keeps the local pi jsonl transcript
  • 会话正文以本地 pi jsonl 为权威源，界面显示的是重建后的投影The local pi jsonl transcript is authoritative; the UI renders a rebuilt projection

Open files from the right-hand tree; each opens in a center tab beside the chat. Multiple files, Markdown edit / preview / split view, and common image previews are supported.

  • UTF-8 文本编辑上限 256 KiB；HTML / SVG 只按源码显示，不执行UTF-8 text edits up to 256 KiB; HTML / SVG show source only and are never executed

  • 未保存草稿不会被目录刷新覆盖；关闭标签或退出窗口前会确认Drafts survive directory refreshes and are confirmed before closing a tab or the window
  • 文件访问限定在当前工作区，符号链接只展示，不展开或预览Access is limited to the current workspace; symlinks are shown but not expanded or previewed

内嵌终端Built-in terminal

中央标签栏的「＋ → 终端」会创建真正的终端标签，PTY 由主进程托管；Windows 默认使用 PowerShell，其他平台启动登录 shell；可在「设置 → 通用」指定命令壳

The center tab bar’s “+ → Terminal” creates a real terminal tab backed by a main-process PTY. Windows defaults to PowerShell; other platforms start a login shell. Choose the shell under Settings → General.

  • 切换对话、文件或工作区不会结束终端进程；关闭终端标签需要确认Switching chats, files, or workspaces keeps the PTY alive; closing a terminal tab asks for confirmation
  • 支持 ANSI、历史滚动、Ctrl+C 与粘贴；输入直接发送给 PTY，不经过模型ANSI, scrollback, Ctrl+C, and paste are supported; input goes straight to the PTY, not through a model
  • 终端与屏幕内容只驻留内存，不写进设置Terminal screens live in memory only and are not written to settings

04 / CONFIGURATION

角色、技能与 MCPRoles, skills, and MCP

角色把提示词、模型、权限与资源打包成一份可复用配置；技能和 MCP 是可挂到角色上的能力

A role packages a prompt, model, permissions, and resources into a reusable profile. Skills and MCP servers are capabilities you attach to it.

角色组成Anatomy of a role

在「设置 → 角色」新建、复制、导入或导出 JSON；一个角色包含以下字段

Create, duplicate, import, or export JSON under Settings → Roles. A role contains:

  • 名称与 idName and idid 只能是小写字母、数字和连字符，保存后不可修改The id allows lowercase letters, digits, and hyphens, and cannot change after saving
  • 系统提示词System prompt追加在基础提示词之后，可以自由修改或清空Appended after the base prompt; edit or clear it freely
  • 模型与思考档位Model and thinking可以指定，也可以跟随会话模型Set explicitly or follow the session model
  • 工具策略与审批档位Tool policy and approval决定能调用哪些工具，以及何时需要你确认Controls which tools are available and when you are asked
  • 技能、MCP 与指令文件Skills, MCP, and instructions选择要加载的资源；指令文件可以覆盖全局选择Pick resources to load; an instruction file can override the global choice

内置 Orchestrator 与 Worker 是默认模板，可以修改并保存，也可以恢复默认；内置 id 固定、不可删除；角色改动对之后新建的会话生效，运行中的会话不会热替换

The built-in Orchestrator and Worker are editable defaults that can be restored; their ids are fixed and cannot be deleted. Role changes apply to newly created sessions; running sessions are not hot-swapped.

工具策略Tool policy

策略Policy可用工具Available tools
全部工具All tools读取、写入、执行命令等 pi 默认编程工具Reading, writes, commands, and the rest of pi’s default coding tools
只读Read-only读文件、只读 git；不能改文件或执行任意命令Read files and read-only git; no writes or arbitrary commands
编排Orchestration只读工具加派发、审查、合并等编排工具；不能写文件或执行任意命令Read-only tools plus dispatch, review, and merge tools; no writes or arbitrary commands

Orchestrator 默认使用「编排」，Worker 默认使用「全部工具」；即使把 Orchestrator 的审批档位设为完全放行，它的工具策略仍然不允许改代码

Orchestrator defaults to Orchestration; Worker defaults to All tools. Even with approval set to Full, the Orchestrator’s tool policy still cannot edit code.

审批档位Approval modes

输入框里可以切换当前会话的审批档位，快捷键是 Shift+Tab；角色里保存的是新建会话时的默认值

Cycle the current session’s approval mode from the composer with Shift+Tab. A role stores the default used by new sessions.

档位Mode行为Behavior
全程审批Supervised命令、文件写改与 MCP 调用都需要确认Commands, file writes and edits, and MCP calls all require confirmation
自动接受编辑Auto-accept edits文件写改自动通过，命令与 MCP 仍要确认File writes and edits pass automatically; commands and MCP still ask
完全放行Full常规工具自动通过，保护操作仍然拦截Ordinary tools pass automatically; protected operations are still intercepted

内置 Orchestrator 的默认审批是「完全放行」，Worker 是「自动接受编辑」；两者都可以在角色里修改

The built-in Orchestrator defaults to Full and the Worker to Auto-accept edits; both are editable in the role.

保护底线Hard floor

git push、git reset --hard、rm -rf、Remove-Item -Recurse、del /s 与包管理器 publish 等保护操作，在任何审批档位下都要你确认；「本会话都允许」也不豁免；10 分钟未答复或回合中止，按拒绝处理

Protected operations such as git push, git reset --hard, rm -rf, Remove-Item -Recurse, del /s, and package-manager publish need your confirmation in every mode. “Allow for session” does not exempt them. No answer within 10 minutes, or an aborted turn, counts as a denial.

技能Skills

在「设置 → 技能」扫描本机，或添加一个包含 SKILL.md 的目录；登记后的技能可以在角色编辑里勾选

Under Settings → Skills, scan this computer or add a folder containing SKILL.md. Registered skills can be selected in the role editor.

  • 扫描来源：Claude Code 的 ~/.claude/skills、Codex 的 ~/.codex/skills、pi 的 ~/.pi/agent/skillsScan sources: Claude Code’s ~/.claude/skills, Codex’s ~/.codex/skills, and pi’s ~/.pi/agent/skills
  • 只登记带 SKILL.md 的目录；同名技能按来源顺序去重Only folders with SKILL.md are registered; duplicates are resolved by source order
  • 移除只删除 Fynvra 里的登记，不删除磁盘上的技能目录Removing a skill only deletes Fynvra’s registry entry, not the folder on disk
  • 技能是否加载由角色的勾选决定；改动在会话下次启动时生效The role decides which skills load; changes take effect the next time a session starts

MCP 服务器MCP servers

在「设置 → MCP」添加服务器，填写名称、传输方式与连接信息；启用后，再到角色里选择要加载的服务器

Add servers under Settings → MCP with a name, transport, and connection details. Enable them, then select which ones a role loads.

传输Transport需要填写Required
本地进程（stdio）Local process (stdio)命令与参数，可选环境变量Command and args, optional environment variables
远程（Streamable HTTP）Remote (Streamable HTTP)URL，可选 HeaderURL, optional headers
远程（SSE）Remote (SSE)URL，可选 HeaderURL, optional headers

「从本机导入」可以读取以下工具的已有配置；重复的服务器会按命令或 URL 标记

Import from this computer reads existing configs from the tools below; duplicates are matched by command or URL.

Claude CodeCodexGrok CLIGemini CLICursorVS CodeOpenCodeCC Switch

环境变量与 Header 的值只在主进程读取，保存后界面不再显示明文；删除一个服务器后，引用它的角色将不再加载它

Environment-variable and header values are read only in the main process and are not shown again after saving. Deleting a server removes it from roles that referenced it.

指令文件Instruction files

本机的 AGENTS.md / CLAUDE.md 类文件可以在「设置 → 指令文件」中导入，以链接或本地副本的形式保存；同一时间只有一份全局指令生效

AGENTS.md / CLAUDE.md-style files can be imported under Settings → Instruction files as links or local copies. Only one global instruction file is active at a time.

  • 链接：每次启动会话时读取源文件；源文件缺失或不可读时显示警告且不注入Link: read at each session start; a missing or unreadable source shows a warning and is not injected
  • 本地副本：保存到 Fynvra 的用户数据目录；编辑链接条目会转为本地副本，绝不改写源文件Local copy: stored in Fynvra’s user-data directory; editing a linked entry converts it to a local copy and never rewrites the source
  • 角色可以跟随全局、不使用，或指定某个条目；指定条目不受全局开关影响A role can follow the global choice, use none, or name an entry; a named entry ignores the global toggle
  • 删除只移除 Fynvra 条目，不会删除磁盘上的原始文件Deleting removes only the Fynvra entry, never the original file on disk

05 / TASKS

任务与更改Tasks and changes

主 Agent 把需求拆成任务，每个任务在独立 worktree 中执行，再经过审查与合并回到主分支

The orchestrator splits a request into tasks, runs each in its own worktree, then brings passing work back through review and merge.

派发条件Before dispatch

git 工作区Git workspace

多 Agent 派发需要已有提交的 git 仓库，并配置 git 用户名与邮箱；Windows 建议安装 Git for Windows；如果找不到 Bash，到「设置 → 通用」指定本地命令壳；非 git 目录走原地模式，见下方说明

Multi-agent dispatch needs a git repository with at least one commit and a configured git user name and email. On Windows, Git for Windows is recommended; if Bash cannot be found, set the local shell under Settings → General. Non-git folders use in-place mode, described below.

一轮完整流程A complete run

  1. 描述需求：在 Orchestrator 会话里说清楚目标，需要时点名角色，例如「Y 交给测试工程师」Describe: state the goal in the Orchestrator session and name a role when needed, for example “give Y to the QA engineer”
  2. 拆解与派发：主 Agent 写任务书，调用 dispatch_task；Fynvra 创建 worktree、启动 Worker 并投递任务书Split and dispatch: the orchestrator writes a brief and calls dispatch_task; Fynvra creates the worktree, starts a worker, and delivers the brief
  3. 并行执行：Worker 在自己的分支里改代码并提交；卡住时用 ask_coordinator 提问，完成后用 report_done 汇报Build in parallel: workers edit and commit on their branches, use ask_coordinator when stuck, and report_done when finished
  4. 审查：主 Agent 用 review_diff 读改动、用 run_checks 跑检查；不达标时用 reject_work 把意见发回Review: the orchestrator reads the diff with review_diff, runs checks with run_checks, and sends work back with reject_work if it falls short
  5. 合并与收尾：通过后 merge_worktree 合入当前分支，cleanup_worktree 清理目录，最后向你汇报结果与证据Merge and wrap up: merge_worktree lands it on the current branch, cleanup_worktree tidies up, and you get a report with evidence

派发后主 Agent 不会阻塞等待，你可以继续对话；收件箱出现完成、提问或上报消息且主 Agent 空闲时，Fynvra 会唤醒它

The orchestrator does not block after dispatching, so you can keep talking to it. When a done, question, or escalation message arrives and the orchestrator is idle, Fynvra wakes it.

任务状态Task states

待开始Not started → 进行中In progress → 待验收In review → 已完成Completed / 失败或已放弃Failed or abandoned

每个任务可以有多次尝试；右侧「任务」按状态分组，点开任务可以查看尝试、消息与结果；待验收的任务在「改动」里选择某次尝试查看 diff

A task can have several attempts. Tasks groups them by state; open a task to see attempts, messages, and results. In Changes, pick an in-review task and attempt to inspect its diff.

编排工具Orchestration tools

这些工具只对使用「编排」策略的角色开放，实际执行由主进程的编排服务完成

These tools are available only to roles using the Orchestration policy; the main-process orchestration service performs the actual work.

工具Tool作用Purpose
dispatch_task创建任务、worktree 与 Worker，并投递任务书Create a task, worktree, and worker; deliver the brief
list_workers列出当前 Run 的 Worker 与状态List workers and states in the current run
wait_for_workers显式等待任意或全部 Worker 完成Explicitly wait for any or all workers
read_worker_output增量读取某个 Worker 的输出Incrementally read one worker’s output
send_to_worker回答提问或发送新的指示Answer a question or send new instructions
review_diff读取任务相对基准提交的改动Read a task’s changes against its base commit
run_checks在任务目录里执行白名单内的检查命令Run a whitelisted check command in the task directory
merge_worktree把 Worker 分支以 --no-ff 合入当前分支Merge the worker branch into the current branch with --no-ff
reject_work把反馈作为新指令发回 WorkerSend feedback back to the worker as a new prompt
cleanup_worktree清理任务目录与分支，或停止原地任务的 WorkerRemove the worktree and branch, or stop an in-place worker

Worker 侧还有两个协议工具：ask_coordinator 阻塞等待主 Agent 回答，report_done 在每一轮只允许成功汇报一次

Workers also have two protocol tools: ask_coordinator blocks until the orchestrator answers, and report_done can succeed only once per run.

审查、打回与合并Review, reject, and merge

  • 审查读取的是 Worker 的提交差异；即使 worktree 已清理，合并时记录的提交范围仍可在「改动」里回看Review reads the worker’s commit range; after cleanup, the commit range recorded at merge time is still viewable in Changes
  • 合并使用 --no-ff；发生冲突时自动中止合并并报告冲突文件，不会留下半合并状态Merges use --no-ff; on conflict the merge is aborted automatically and conflicting files are reported
  • 打回会把反馈作为新的提示词发回 Worker，Worker 可以再次修改并汇报Rejecting sends feedback as a new prompt; the worker can revise and report again
  • 合并到主 Agent 当前检出的分支；合并前会确认仓库仍在该分支上Work merges into the branch the orchestrator has checked out; Fynvra verifies the repo is still on it first
  • 派发时的审批档位跟随主 Agent 当时的档位；Worker 的保护操作仍走同一条底线A dispatched worker inherits the orchestrator’s approval mode at dispatch time; protected operations still hit the same hard floor

没有 git 的工作区Workspaces without git

普通文件夹按原地模式编排：不创建 worktree，Worker 的 cwd 就是工作区目录；review_diff 没有 diff，改为列出 Worker 在汇报里提交的改动文件；merge_worktree 直接把任务记为完成；cleanup_worktree 只停止 Worker，改动留在目录里

Plain folders run in place: no worktree, and the worker’s cwd is the workspace folder. review_diff has no diff and lists the files reported by the worker instead; merge_worktree marks the task complete; cleanup_worktree only stops the worker and leaves changes in the folder.

并行 Worker 会共用同一个目录与文件，建议一次只派发一个任务；需要隔离时，把目录初始化为 git 仓库并至少提交一次

Parallel workers share the same folder and files, so dispatch one task at a time. For isolation, initialize the folder as a git repository and make at least one commit.

用量与通知Usage and notifications

「设置 → 用量」从本机会话记录汇总 Token、费用、缓存命中率，以及本期任务的完成、放弃、失败状态、打回次数与一次验收通过率；未知或已删除的会话单独归组，不返回路径和正文

Settings → Usage summarizes tokens, cost, cache hit rate, and this period’s completed, abandoned, and failed task states, rejections, and first-pass acceptance from local session records. Unknown or deleted sessions are grouped separately; paths and message content are not returned.

通知可以只针对主 Agent 完成、Worker 提问、上报与审批请求；桌面通知和声音在「设置 → 通知」里控制

Notifications can be limited to orchestrator completion or extended to worker questions, escalations, and approval requests. Desktop notifications and sound are controlled under Settings → Notifications.

06 / FAQ

常见问题FAQ

平台、数据、更新与迁移相关的短答案；具体操作回到前五章

Short answers on platforms, data, updates, and migration. Detailed steps live in the first five chapters.

没有 Release 或安装包怎么办No release or installer yet?

按「从源码运行」安装 Node.js 22.19+、pnpm 10.26.2 与 Git，执行 pnpm install --frozen-lockfile 后运行 pnpm dev

Follow “Run from source”: install Node.js 22.19+, pnpm 10.26.2, and Git, run pnpm install --frozen-lockfile, then pnpm dev.

Windows SmartScreen 或 macOS Gatekeeper 拦截了安装包Windows SmartScreen or macOS Gatekeeper blocked the installer

没有签名证书的 Windows 包可能触发 SmartScreen；没有 Apple 凭证的 Mac 包是临时签名；确认下载来源可信后再按系统提示放行，不建议全局关闭安全检查

Unsigned Windows builds may trigger SmartScreen; Mac builds without Apple credentials are ad-hoc signed. Verify where the download came from, then follow the system prompt for this app. Do not disable security checks globally.

必须用 git 吗Is git required?

不是，普通文件夹按原地模式工作，但不创建 worktree，并行 Worker 会共用目录；需要隔离与逐任务 diff 时使用 git 仓库

No. Plain folders run in place, but without worktrees, so parallel workers share the folder. Use a git repository when you need isolation and per-task diffs.

主 Agent 会自己改代码吗Does the orchestrator edit code itself?

默认不会，它的工具策略只包含读文件、只读 git 和编排工具；你可以修改角色配置，但运行时仍会执行工具权限与审批底线

Not by default. Its tool policy includes only file reads, read-only git, and orchestration tools. You can edit the role, but the runtime still enforces tool permissions and the approval floor.

代码、会话和密钥会被上传吗Are code, sessions, and keys uploaded?

Fynvra 没有中转服务器，模型请求只发往你配置的服务地址；设置、角色、会话与密钥保存在本机应用数据目录；密钥明文只在主进程使用，但本地配置不是加密凭证库，请不要分享用户数据目录；Agent 与 MCP 仍可能执行命令或访问外部服务，按项目需要设置工具策略与审批档位

There is no relay server; model requests go only to the endpoints you configure. Settings, roles, sessions, and keys stay in the local app-data directory. Plaintext keys are used only in the main process, but local config is not an encrypted vault, so do not share the user-data folder. Agents and MCP servers can still run commands or reach external services, so set the tool policy and approval mode for the project.

能连接本地模型吗Can I connect a local model?

只要服务实现了受支持的四种协议之一，就可以填自定义 Base URL、API Key 与模型 id 接入；Fynvra 不内置模型运行时，也不代为安装推理服务

If a server implements one of the four supported protocols, point a provider at its base URL with an API key and model id. Fynvra does not bundle a model runtime or install inference servers.

Worker 会 push 或删库吗Can workers push or delete a repository?

git push、git reset --hard、rm -rf 等保护操作在任何审批档位下都必须由你确认；没有回应按拒绝处理

Protected operations such as git push, git reset --hard, and rm -rf always require your confirmation, regardless of approval mode. No response means denial.

支持哪些平台，Linux 能用吗Which platforms are supported? What about Linux?

正式提供 Windows x64 与 macOS Intel / Apple Silicon 安装包，Linux 有 AppImage 构建配置，但尚未纳入自动发布、安装包分发与更新

Windows x64 and macOS Intel / Apple Silicon are the released platforms. Linux has an AppImage build config but is not part of automated releases, installer distribution, or updates.

如何更新，开发模式会更新吗How do updates work? Does dev mode update?

Windows 安装版与正式签名的 macOS 版启动后及每 4 小时检查一次稳定版，下载完成后等你确认安装；未签名 Mac 包从 Releases 手动覆盖，开发模式与未发布平台不联网更新

Installed Windows and Developer ID-signed macOS builds check for stable updates at startup and every 4 hours, then wait for your confirmation. Unsigned Mac builds are replaced manually from Releases. Dev mode and unpublished platforms do not update online.

数据存在哪里，开发版和正式版会混用吗Where is data stored? Do dev and release builds share it?

设置、角色、模型服务、MCP 与会话都在本机应用数据目录；开发版使用 fynvra-dev，与安装版分开；只有开发模式认 FYNVRA_USER_DATA_DIR；删除会话不会删除 pi jsonl 正文记录

Settings, roles, providers, MCP, and sessions live in the local app-data directory. Dev builds use fynvra-dev, separate from installed builds; FYNVRA_USER_DATA_DIR applies only in dev mode. Removing a session does not delete its pi jsonl transcript.

可以从 Claude Code、Codex 迁移吗Can I migrate from Claude Code or Codex?

模型服务可从 Claude Code、Codex、CC Switch 导入；MCP 额外支持 Grok CLI、Gemini CLI、Cursor、VS Code 与 OpenCode；技能会扫描 Claude Code、Codex 与 pi 的目录；导入前可预览并去重

Providers can be imported from Claude Code, Codex, and CC Switch; MCP also supports Grok CLI, Gemini CLI, Cursor, VS Code, and OpenCode; skills are scanned from Claude Code, Codex, and pi. Preview and deduplicate before importing.

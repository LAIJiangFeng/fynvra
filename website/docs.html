Docs使用文档User guide

从安装到第一次派发。From install to the first dispatch.

Fynvra 在本机运行。你只和主 Agent 对话，它把需求拆成任务，交给各自独立的 Worker，再审查并合并。

Fynvra runs on your machine. You talk to one orchestrator; it splits the work, hands each piece to its own worker, then reviews and merges.

Windows x64 · macOS 本地优先 · 无中转服务器 Local-first · no relay server

概览Overview

窗口分成三块：左侧是工作区和会话，中间是对话、文件和终端，右侧是编排面板，里面有任务和改动。

The window has three areas: workspaces and sessions on the left, chat, files, and the terminal in the center, and the orchestration panel on the right with tasks and changes.

工作区Workspace
挂进来的一个目录。有 git 时按仓库编排；没有 git 时按原地模式工作。 A folder you attach. Git repos use the orchestration flow; folders without git run in place.
会话Session
一次和某个角色的对话。状态有空闲、运行中、等待审批、出错。 A conversation with one role. Status is idle, running, waiting for approval, or error.
Orchestrator
主 Agent。拆任务、派活、审查、合并。默认自己不改代码。 The main agent. It plans, dispatches, reviews, and merges. By default it does not edit code.
Worker
接到一个任务的 Agent。在自己的 git worktree 里改代码，做完向主 Agent 汇报。 An agent given one task. It edits inside its own git worktree and reports back.
收件箱Inbox
Worker 和主 Agent 之间的消息：提问、答复、指示、完成汇报。主 Agent 空闲时会被唤醒。 Messages between a worker and the orchestrator: questions, replies, instructions, and done reports. An idle orchestrator is woken up.

安装Install

安装包发布后从 GitHub Releases 下载。还没有 Release 时，按下面的步骤从源码运行。

When installers are published, download them from GitHub Releases. If none is available yet, run from source.

平台Platform 安装包Installer 更新Updates
Windows x64 NSIS .exe 已接入自动更新Auto-update wired up
macOS Intel / Apple Silicon .dmg / .zip 签名公证后可自动更新；未签名包需手动覆盖安装 Auto-update after signing and notarization; unsigned builds are manual
Linux AppImage 有构建配置，尚未纳入自动发布与更新Build config exists; not in automated releases yet
macOSmacOS

第一次安装先把应用从 DMG 拖进「应用程序」再打开。没有 Apple 凭证的包是临时签名，系统可能提示无法验证开发者。确认来源可信后，到「系统设置 → 隐私与安全性」里对本应用选择「仍要打开」。不需要关闭系统安全检查。

On first install, drag the app from the DMG into Applications before launching. Builds without Apple credentials are ad-hoc signed, so macOS may say the developer cannot be verified. After you trust the source, choose Open Anyway for this app under System Settings → Privacy & Security. You do not need to turn system security checks off.

从源码运行Run from source

需要 Node.js 22.19.0 或更高（推荐 22）、pnpm 10.26.2，以及 Git。

You need Node.js 22.19.0 or later (22 recommended), pnpm 10.26.2, and Git.

bash
npm install --global pnpm@10.26.2
git clone https://github.com/LAIJiangFeng/fynvra.git
cd fynvra
pnpm install --frozen-lockfile
pnpm dev

第一次运行要联网下载依赖和 Electron。开发版的数据目录是系统应用数据目录下的 fynvra-dev，和正式版分开。仓库里不需要 .env，模型密钥在设置界面里填写。

The first run needs network access to download dependencies and Electron. Dev builds store data in fynvra-dev under the system app-data directory, separate from release builds. The repo does not need a .env; add model keys in Settings.

快速开始Quick start

  1. 添加模型服务Add a model provider

    按 Ctrl+,（macOS 为 ⌘+,）打开设置，进入「模型服务」。添加一个服务，或从本机已有配置导入。

    Press Ctrl+, (⌘+, on macOS) and open Model providers. Add one, or import from configs already on this computer.

  2. 挂入目录Attach a folder

    在左侧「工作区」点「挂入目录」，选一个仓库或普通文件夹。

    Under Workspaces in the sidebar, choose Attach folder and pick a repo or a plain folder.

  3. 新建会话Start a session

    点「新建会话」。多 Agent 协作选内置的 Orchestrator，选好模型和思考档位后创建。

    Choose New session. For multi-agent work, pick the built-in Orchestrator, then a model and thinking level.

  4. 说清楚要做什么Describe the goal

    用你平时的语言写需求。主 Agent 会拆任务并派发。进度、提问和改动出现在右侧「编排」里。

    Write the request in your own language. The orchestrator splits it and dispatches. Progress, questions, and diffs show up under Orchestration on the right.

派发条件Dispatch needs git

多 Agent 派发需要一个已有提交的 Git 仓库，并且本机配置了 Git 用户名和邮箱。Windows 上建议安装 Git for Windows；如果找不到 Bash，到「设置 → 通用」里指定 Windows 本地命令壳。

Dispatch needs a Git repository that already has commits, plus a Git user name and email. On Windows, Git for Windows is recommended; if Bash cannot be found, set the local agent shell under Settings → General.

模型服务Providers

在「设置 → 模型服务」里添加。可以选择预设，也可以用自定义 OpenAI 兼容地址。填写名称、API 协议、Base URL、API Key 和模型 id。官方地址可以留空。

Add them under Settings → Model providers. Pick a preset or a custom OpenAI-compatible endpoint. Fill in the name, API protocol, base URL, API key, and model id. The official base URL can be left blank.

  • 测试连接会显示耗时，以及服务端返回了多少个模型。 Test connection reports latency and how many models the server returned.
  • 拉取模型列表把远端模型加进来；也可以手动输入模型 id。 Fetch models adds remote models; you can also type a model id yourself.
  • 推理打开后，会话里才能选思考档位。 Turn Reasoning on to choose a thinking level in chat.
  • 从本机导入会读取 Claude Code、Codex、CC Switch 里已有的服务。没有 API Key 或自定义地址的配置不会出现。 Import from this computer reads providers from Claude Code, Codex, and CC Switch. Configs without an API key or custom URL are skipped.
密钥Keys

API Key 的明文只在主进程使用，界面上回显成掩码。它保存在本机配置文件里，不是加密凭证库。不要把应用数据目录、配置导出或带密钥的日志发给别人。删除一个服务后，引用它的角色需要重新选择模型。

Plaintext API keys stay in the main process; the UI shows a mask. They are stored in local config files, not an encrypted vault. Don't share the app data folder, config exports, or logs that contain keys. After you delete a provider, roles that used it need a new model.

思考档位Thinking

思考档位决定模型在回答前想多深。在模型选择器、新建会话和角色编辑里切换。模型服务上的「推理」没打开时，这个选项不会出现。

The thinking level is how deeply the model reasons before it answers. Change it in the model picker, the new-session dialog, or the role editor. It only appears when Reasoning is on for that model.

档位Level 含义Meaning
off 关闭思考No thinking
minimal 极少思考Barely any
low 少量思考Light
medium 适中，日常改代码用这个就够Balanced; enough for everyday edits
high 深入思考Deep
xhigh 更深入思考Deeper
max 最大思考。更慢，也更耗额度Maximum. Slower, and uses more of your quota

某个模型在目录里没有档位信息时，界面会标明这是按协议兜底，或暂时读不到档位。

If a model has no level catalog, the UI marks the choice as a protocol fallback, or says the levels could not be read.

角色Roles

角色是一套可复用的配置：提示词、模型、思考档位、工具策略、审批档位、技能、MCP 和指令文件。在「设置 → 角色」里新建、复制、导入或导出 JSON。内置角色可以改，也可以恢复默认。改动对之后新建的会话生效。

A role is a reusable bundle: prompt, model, thinking level, tool policy, approval mode, skills, MCP, and instruction files. Create, duplicate, import, or export JSON under Settings → Roles. Built-in roles can be edited and restored. Changes apply to sessions you create afterwards.

内置角色Built-in 工具策略Tool policy 默认审批Default approval
Orchestrator 编排Orchestration 完全放行Full
Worker 全部工具All tools 自动接受编辑Auto-accept edits

工具策略有三档：

There are three tool policies:

  • 全部工具：可以读、写、执行命令。Worker 默认用这个。 All tools: read, write, and run commands. This is the Worker default.
  • 只读：不能改文件，也不能执行任意命令。 Read-only: no file edits and no arbitrary commands.
  • 编排：读文件、只读 git，以及派发、审查、合并等编排工具。不能写文件或执行任意命令。Orchestrator 默认用这个，所以即使审批是「完全放行」，它自己也不会改代码。 Orchestration: read files, read-only git, and the dispatch, review, and merge tools. No writes and no arbitrary commands. This is why the Orchestrator still doesn't edit code when its approval mode is Full.

角色 ID 只能是小写字母、数字和连字符，保存后不能改。派发时如果没有指定角色，用默认的 Worker。

A role id is lowercase letters, digits, and hyphens, and it cannot be changed after save. Dispatch uses the Worker role when none is named.

编排Orchestration

主 Agent 的一轮工作通常是这样：

A typical orchestrator loop looks like this:

  1. 拆任务Split the work

    读够用的代码，把需求分成边界清楚、尽量能并行的任务，并写一份 Worker 能独立执行的任务说明。

    Read just enough code to split the request into tasks with clear ownership, then write a brief each worker can follow on its own.

  2. 派发Dispatch

    每个任务一个 Worker，单独的 git worktree，分支名是 fynvra/<slug>。默认放在仓库同级的 <仓库目录名>-worktrees，可在「设置 → 通用」里改位置。

    Each task gets its own worker and git worktree on fynvra/<slug>. By default that folder sits beside the repo as <repo>-worktrees. Change the location under Settings → General.

  3. 验收Review

    Worker 汇报后，主 Agent 看 diff、跑检查。通过就合并（merge --no-ff）并清理 worktree；不行就打回，Worker 再改。

    When a worker reports done, the orchestrator reads the diff and runs checks. A pass is merged with merge --no-ff and the worktree is cleaned up; otherwise the work is sent back.

任务状态：

Task status:

待开始Not started → 进行中In progress → 待验收In review → 已完成Completed

走不下去时会标成失败或已放弃。右侧「改动」页列出尚未合并的文件。

Work that cannot continue is marked failed or abandoned. The Changes tab lists files that are not merged yet.

没有 gitNo git

普通文件夹走原地模式：不建 worktree，Worker 直接改这个目录，审查时列出它汇报的文件。并行的 Worker 会共用同一份文件，一次只派一个任务。

A folder without git runs in place: no worktree, workers edit that folder, and review lists the files they reported. Parallel workers would share those files, so dispatch one task at a time.

审批Approvals

输入框里可以切换审批档位，快捷键是 Shift+Tab。角色设置里也有一份默认值，新建会话时带上。

Cycle the approval mode from the composer with Shift+Tab. Roles store a default that new sessions start with.

档位Mode 行为Behavior
全程审批Supervised 执行命令、编辑文件、写入文件、调用 MCP 都要你点允许。Commands, edits, writes, and MCP calls wait for Allow.
自动接受编辑Auto-accept edits 文件编辑和写入自动通过，命令和 MCP 仍要审批。Worker 默认是这个。File edits and writes pass automatically; commands and MCP still ask. This is the Worker default.
完全放行Full 常规工具自动通过。Orchestrator 默认是这个，但它的工具策略仍然不能改代码。Ordinary tools pass automatically. This is the Orchestrator default, and its tool policy still cannot edit code.
保护底线Hard floor

git push、git reset --hard、rm -rf 这类保护操作，在任何审批档位下都要你确认。「本会话都允许」也不会豁免。

Protected operations such as git push, git reset --hard, and rm -rf need your confirmation in every approval mode. Allow for session does not exempt them.

数据与更新Data and updates

设置、角色、模型服务、MCP 和会话都在本机应用数据目录里，不要提交到 Git，也不要打包发给别人。开发版默认用 fynvra-dev，和安装版分开。只有开发模式才认环境变量 FYNVRA_USER_DATA_DIR。

Settings, roles, providers, MCP, and sessions live in the local app data directory. Don't commit that folder or send it to anyone. Dev builds use fynvra-dev, separate from an installed release. FYNVRA_USER_DATA_DIR is honored only in dev mode.

文件读写限制在已挂入的工作区。渲染进程不能直接使用 Node.js 或 Electron。Agent 和 MCP 仍然可以执行命令或访问外部服务，所以工具策略和审批档位要按项目来设。

File access is limited to attached workspaces. The renderer cannot use Node.js or Electron directly. Agents and MCP can still run commands or reach external services, so set the tool policy and approval mode for the project.

已安装的 Windows 版，以及带 Developer ID 签名的 macOS 版，会在启动时和之后每 4 小时检查更新，下载完成后等你确认再重启安装。未签名的 Mac 包请从 Releases 手动下载覆盖。开发模式（pnpm dev）不检查更新。Linux 目前没有自动更新。

Installed Windows builds, and macOS builds signed with a Developer ID, check at startup and every 4 hours. The download installs after you confirm a restart. Unsigned Mac builds are replaced by hand from Releases. Dev mode (pnpm dev) does not check for updates. Linux has no auto-update yet.

<span id="orchestration" />

你只和主 Agent 对话。它读代码、拆任务、为每个任务派一个 Worker，再审查结果、合并或打回。界面上的「任务」和「改动」是这条流程的只读视图；控制通过对话完成。

<span id="orchestration-loop" />

## 一轮编排

1. ### 拆任务

   读够用的代码，把需求分成边界清楚、尽量能并行的任务，并写一份 Worker 能独立执行的任务说明。任务之间的依赖会记在派发里。

2. ### 派发

   在 Git 工作区，每个任务一个 Worker，单独的 git worktree，分支名是 `fynvra/<slug>`。默认放在仓库同级的 `<仓库目录名>-worktrees`，可在「设置 → 通用」里改位置。普通文件夹不建 worktree：Worker 直接在挂入的目录里改，同一目录一次只派一个任务。没有指定角色时用默认的 Worker。

3. ### 验收

   Worker 汇报后，主 Agent 看 diff、跑检查。通过就合并（`merge --no-ff`）并清理 worktree；不行就打回，Worker 再改，形成新的尝试。

<span id="orchestration-conditions" />

## 派发方式与默认边界

- **Git 仓库（worktree 隔离）**：已有一个提交，且本机配置了 Git 用户名和邮箱。每个任务在独立 worktree 中执行；Windows 上建议安装 Git for Windows，找不到 Bash 时在「设置 → 通用」指定 Windows 本地命令壳。
- **普通目录（原地模式）**：不需要 Git，Worker 直接修改挂入的目录；同一目录一次只派一个任务，也没有 worktree diff。
- **默认 Worker**：派发时没有指定角色就用 Worker；Worker 默认「全部工具 + 自动接受编辑」。
- **主 Agent 不改代码**：Orchestrator 的工具策略是「编排」，只能读、只读 Git 和派发/审查/合并工具，即使审批是「完全放行」也不能写文件或执行任意命令。
- **任务状态**：待开始 → 进行中 → 待验收 → 已完成；走不下去会标成失败或已放弃。改动以未提交 / 已提交分组，在任务详情里查看。

<span id="orchestration-control" />

## 你如何控制流程

在主 Agent 的输入框里补充需求、回答问题、要求重试、打回或合并。任务抽屉不提供合并 / 打回按钮：它展示任务书、依赖、尝试、消息、Worker 输出和改动，具体决定由主 Agent 执行。

需要你确认的工具调用会出现在审批条或顶部提示条；审批档位决定普通操作是否需要逐步确认。无论当前档位如何，受保护的操作仍要单独确认，见 [审批](/zh/docs/approval/)。
